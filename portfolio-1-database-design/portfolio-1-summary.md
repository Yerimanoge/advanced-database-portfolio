**Case study.** Akira is a fintech cryptocurrency platform in which users hold wallets, send crypto to other users and pay businesses that accept it. Every balance and transaction uses one currency unit. The database supports regular users, merchants and data analysts, and stores users, devices, wallets, addresses, merchants, transactions and ledger entries. Its key operations are wallet transfers, merchant payments, reversals that preserve history, balance auditing and analytical reporting. The starting data is the synthetic *Cryptocurrency Transaction Insights* dataset (DatabaseSample, 2026), accessed on 15 October 2026.

**Original design and its limits.** The dataset provided users, wallets, devices, addresses and transactions. Each transaction pointed to a single wallet, so it could not express a sender and a recipient. There was no transaction type or status, no ledger and no merchants table. Wallet balances (26 of 152) and transaction amounts (31 of 343) could be NULL, which would let the no-overdraft rule be bypassed.

**Final design.** The final relational schema has seven tables (see Figure 1: ER diagram). Wallets gained a wallet type and an opening balance. Transactions gained a type (transfer or payment), a status (pending, completed, failed or reversed) and a recipient wallet, with the existing wallet column acting as the sender. A ledger_entries table records signed amounts, where a negative value is money out and a positive value is money in, together with the balance after each entry. A merchants table links each merchant to one user and one wallet, with a unique business name. Every table has a primary key, and foreign keys keep all references valid. A composite foreign key ensures that a merchant's wallet belongs to the user who registered the merchant.

**Constraints and business rules.** Amounts must be positive, a wallet cannot send to itself, and balances cannot be negative or NULL. The last rule enforces that a wallet cannot send more than it holds. A unique key on transaction, wallet and entry kind prevents duplicate ledger postings and duplicate reversals. These rules were tested by statements that were expected to fail (Figure 2): the database returned error 3819 for a negative balance, a self-transfer and a zero amount, and error 1062 for a second merchant account for the same user.

**Normalisation.** The tables are in third normal form: each non-key column depends only on its table's key. Three deliberate exceptions improve speed or audit: the stored wallet balance (derivable from the opening balance and the ledger), the balance-after column on ledger entries, and the wallet type column. A balance audit compares stored balances with ledger totals and reports differences without correcting them.

**Migration and problem solving.** The original dataset was kept unmodified and the working tables were backed up into a separate database. Changes were made with numbered scripts. One script stopped with MySQL error 1832, because a foreign-key column cannot be changed from NULL to NOT NULL while foreign key checks are on; a continuation script switched checks off for two statements on empty tables and then switched them on again. Because the 343 original transactions had no recipient, type or status, they were removed from the working database and replaced later with generated, clearly labelled transactions. Five merchants and their wallets were also generated.
